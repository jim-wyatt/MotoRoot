# VedoTom image: review findings and backlog

Review of the image built on the Legion T5 on 2026-11-17 at 11:59 EST:
`Android/vedotom_arm64/generic_arm64:Baklava/BP4A.251205.006/eng.sysadm:userdebug/test-keys`.
It was installed by DSU on the XT2617V (24 GB data partition, Wi-Fi, no SIM) and checked from
adb about four minutes after first boot. The stock system is not affected by anything here.

Work these on the Legion.

## What works

- It boots: about 37 s to the lock screen, with no boot animation as intended. SELinux is enforcing. The crash log, tombstones and ANRs are all empty.
- The first-boot service finished in 11.6 s. Fennec and Organic Maps are installed with F-Droid as installer. HOME, BROWSER, DIALER and SMS go to Fossify Launcher, Fennec, Fossify Phone and Fossify Messages. All 16 Fossify apps have the teal icon.
- `gpuservice` stays up, so the BpfMap patch holds.
- Hardware works: Wi-Fi (5 GHz, validated), Bluetooth, NFC, GNSS, 2 cameras, the full sensor list (including the Motorola gestures), fingerprint HAL, audio, thermal and 120 Hz display modes. Cellular is untested because there's no SIM.
- The only SELinux denials are 34 from the vendor's `batt_health` reading `default_prop`, plus one `statsbootstrap` lookup.

## 1. Make it match the clean development baseline (priority)

**Done and validated on the device (2026-11-17, image built 17:16 from b3feb8f, SHA-256 `37758764…0414fb`).** No Organic Maps, Fennec or F-Droid client, and no `/product/etc/preload`. The 16 Fossify apps have teal icons, and Fossify Launcher holds HOME. The Files icon is hidden, and OPEN_DOCUMENT, GET_CONTENT and CREATE_DOCUMENT still resolve to DocumentsUI. All three animation scales, `verifier_verify_adb_installs` and `adb_allowed_connection_time` are 0. All four log buffers are 16 MiB. First boot reports `done failures=0`, and the crash log, tombstones and ANRs are empty. Links (`https://…`) now resolve to nothing, as intended without a browser. All four points below are in place. Two details differ from the suggestions: the development settings are set by the first-boot service, not a SettingsProvider overlay, because SettingsProvider has resource defaults for only two of the five in this tag; and the log size is set by an init rule running `logcat -G 16M` on `logd.ready`, because logd ignores `ro.logd.size` and `persist.logd.size` at start on a phone (it reads them only on automotive and desktop hardware types). [What's in the image](aosp-build.md#whats-in-the-image) describes the result.

The stock system was reduced to a clean development baseline on 2026-11-17 (commits 5300f04 and f895d9b). The image and the deploy loop haven't caught up yet.

  - the release-config override in `release/`. It exists only because Gecko calls `MessageQueue.next()`, so `trunk_staging`'s default queue is fine again.
  - the Organic Maps and Fennec pins in `dev/toolchain.json`. **Keep the F-Droid pin**, because the stock baseline still has the F-Droid client installed.
  - the maps step from `Deploy-Image.ps1` (`-NoMaps`, `-Region`), and `Push-OfflineMaps.ps1` with the `work\organicmaps` copy it reads
  - the matching text in `aosp-build.md` ("What's in the image", "Fennec and the MessageQueue flag", "Offline maps", the Deploy-Image description), and anywhere else these apps are mentioned (credits, NOTICE, README, validation)

  What follows from this: the image has no web browser (Browser2 was removed for Fennec and stays out), and nothing updates the Fossify apps on the device. They're updated by re-pinning them and shipping a new image. Fossify Keyboard stays, and LatinIME stays the default and fallback.
- **Hide the AOSP Files icon; Fossify File Manager replaces it.** DocumentsUI can't be removed: it's the system file picker behind every open, get-content and save dialog (`.picker.PickActivity`), Fossify apps included. Only its launcher entry, `com.android.documentsui/.LauncherActivity`, needs to go. Tested on this image: after `pm disable com.android.documentsui/.LauncherActivity` the icon is gone, and OPEN_DOCUMENT, GET_CONTENT and CREATE_DOCUMENT still resolve to DocumentsUI's picker. Add it to `vedotom-firstboot.sh` as a once-only step with a marker, like the HOME role, then force-stop `org.fossify.home`. If DocumentsUI's manifest gates that alias on a resource flag in this tag, an overlay value is cleaner than first boot doing it. Check `packages/apps/DocumentsUI/AndroidManifest.xml` in the tree.
- **The development settings aren't in the image.** The animation scales are 1.0, and `verifier_verify_adb_installs` and `adb_allowed_connection_time` are unset. Either set their defaults in the image (a SettingsProvider overlay: `def_window_animation_scale`, `def_transition_animation_scale`, plus the global settings) or run `Set-DevSettings.ps1` as a Deploy-Image step. The overlay is better: it survives a Discard and needs no PC.
- **Log buffers are 256 KiB.** On the stock system they're 16 MiB. In the image, the first-boot service's log lines had already rotated out of every buffer four minutes after boot. Set `ro.logd.size=16M` (or `persist.logd.size`) in `PRODUCT_PRODUCT_PROPERTIES`, and check with `logcat -g` that this logd honours it. On stock it didn't, which is why `dev_debuggable` 1.3 re-applies it.

## 2. Correctness

**Done and validated on the 17:16 image:** the time zone (the clock reads EST) (`persist.sys.timezone=America/New_York` as the product default) and the first-boot result (a `log` and a `status` file in `/data/local/vedotom-firstboot/`, which `Deploy-Image.ps1` now reads instead of logcat). The other three points are open.

- **The time zone is GMT.** Auto time zone is on, but with no SIM the telephony suggestion (MCC 310, `America/New_York`, match type 2: the US has several offsets) isn't applied, and there's no location time-zone provider (`mGeoDetectionSupported=false`). Ship a default `persist.sys.timezone` (product property) or let first boot set it. Location time-zone detection needs a provider, which AOSP doesn't ship without GMS.
- **The first-boot result relies on logcat.** `Deploy-Image.ps1` waits for `vedotom-firstboot: done` in logcat, and its report counts preloads and icons from logcat too. With 256 KiB buffers and vendor log spam (below), those lines can roll out within minutes: here they already had. Have the script also append to `/data/local/vedotom-firstboot/log` and set a property when it's done, then make Deploy-Image read those.
- **Vibration amplitude errors.** There were 17 `DefaultHalVibrator: Error setting amplitude to -1.0` failures (IllegalArgumentException from `IVibrator.setAmplitude`). The framework sends the "default amplitude" sentinel to a HAL that rejects it. Check `config_vibratorSupportsAmplitudeControl` and the HAL capabilities. The fix is probably a framework overlay value or a small patch in `VintfHalVibrator`. **Fixed for the next image:** the framework stores amplitude -1 ("unknown") when the vibrator turns on, and `SetAmplitudeVibratorStep.turnVibratorBackOn` passes that value back to `setAmplitude`. The HAL (`android.hardware.vibrator-service.mediatek`, capabilities `AMPLITUDE_CONTROL` only) rejects it. `dev/aosp/patches/frameworks-base-0001-vibrator-no-unknown-amplitude-to-hal.patch` makes `VintfHalVibrator.setAmplitude` skip negative values, so the vibrator keeps its strength.
- **Wi-Fi binder errors.** 34 `FAILED BINDER TRANSACTION` and 15 `Outgoing transactions from this process must be FLAG_ONEWAY` stack traces in `IWifiManager.onTransact`, from `ParceledListSlice`. Find the caller (probably the Settings Wi-Fi picker or the passpoint lookup; `WifiService: Attempt to retrieve passpoint with invalid scanResult List`) before deciding whether it matters. **Closed (2026-11-17, re-diagnosed on the 17:16 image):** opening the Wi-Fi picker produced no binder failures. The two FLAG_ONEWAY traces of that boot were system_server calls on oneway-only threads (`IVibrator.getCapabilities` at vibrator init, `IBluetooth.getProfile` when Bluetooth turns on): log noise, not this image's doing. What remains is `WifiService: Attempt to retrieve passpoint with invalid scanResult List` when the picker opens, which is harmless.
- **Charge cap.** The phone lives on the charger, and the stock system caps at 80% through Moto Actions, which the image doesn't have. It was charging at 93% here. There's no `charge_control_limit` node. Look at the MediaTek and Motorola charger sysfs (`mtk-master-charger`, `/sys/module/mmi_*`) for a stop or limit control that the first-boot service or an init rule could set. The `batt_health` denials above may be related. **Done for the next image:** stock's chain (Moto Actions, then a Moto service in system_server, then the vendor HAL `motorola.hardware.health-service`) ends in one write of 80 to `/sys/module/qpnp_adaptive_charge/parameters/upper_limit` with `lower_limit` -1. Stock's `dumpsys battery` shows `AdaptiveCharging ... mUpperLimit:80, mLowerLimit:-1`, and MediaTek smart charging's nodes read the same with protection on and off. The image now makes that write itself, from `persist.vedotom.charge_limit` (default 80). A hand test first: at 100% on the charger, `blocking` went 0 to 1 and the status to "Not charging", as on stock. The `batt_health` denials are unrelated: that daemon reads a battery first-use-date property.

## 3. Trim and harden (lower priority)

- **ADB needs no authorisation:** `ro.adb.secure=0`. Any USB host gets a root-capable shell on this userdebug image. That's convenient on a desk, but it should be a deliberate choice, and `ro.adb.secure=1` costs one tap per new PC. adb isn't listening on TCP.
- **The AOSP keyboard has its own app-drawer icon** (`com.android.inputmethod.latin/.setup.SetupActivity`, "Android Keyboard settings"), next to Fossify Keyboard's. Hide it the same way as the Files icon. Its settings stay reachable from Settings, System, Keyboard. **Done for the next image:** first boot now disables it the same way as the Files icon.
- **Remove the Virtualization packages.** `vedotom_arm64.mk` inherits `packages/modules/Virtualization/apex/product_packages.mk`, and `com.android.compos` is in the image deps, but this SoC has no AVF (`com.android.virtualization.terminal` is disabled). That's dead weight in a full system partition. **Done for the next image:** `vedotom_arm64.mk` no longer inherits the Virtualization product packages, and `com.android.compos` is out of the image deps. `com.android.virt` stays, because `base_system.mk` installs it and its jar is on the classpath; without `PRODUCT_AVF_ENABLED` it builds its variant for devices without AVF.
- **Unneeded AOSP apps:** PhotoTable and BasicDreams, `com.android.egg`, Bips (print), PrintSpooler, HtmlViewer, BookmarkProvider, CallLogBackup, WallpaperBackup. Keep Traceur: it's useful for development. Each one has to come out of the makefiles and the `Android.bp` mirror together. **Partly done:** PhotoTable is out (it lives in the product makefiles this project already mirrors). The others are on the system partition, which comes from upstream's `base_system.mk`, `handheld_system.mk`, `telephony_system.mk` and `media_system.mk` and from `system_image_defaults` in `build/make/target/product/generic/Android.bp` (about 600 lines). Neither make nor Soong can subtract a package, so removing them means mirroring all of that, to be re-checked on every tag move. That's a decision for the user, proposed separately.
- **Google endpoints still in use:** captive-portal checks (`connectivitycheck.gstatic.com`, `www.google.com`) and NTP (`time.android.com`). If avoiding Google as far as practical applies to the image too, set `captive_portal_*_url` and `config_ntpServer` in the overlay, for example to a self-hosted or neutral endpoint and `pool.ntp.org`.
- **WebView is AOSP's 140.0.7339.4 from the tag.** Nothing updates it in this image, so it ages with the tag. With Fennec gone, it's the only web engine on the device.
- **Security patch level 2025-11-05** (tag android-16.0.0_r4) under a 2026-04-01 vendor patch level. Move the tag when a newer Android 16 QPR release is out, and expect the `Android.bp` mirror and the patches to need rebasing.

1. **Faster image transfer: publish the image in parts.** Benchmark from the install PC (256 MB each, tunnel up, ping 10/10):

   | Method | Time | Speed |
   | --- | --- | --- |
   | scp (as today) | 118.3 s | 2.16 MB/s |
   | scp aes128-gcm | 130.3 s | 1.96 MB/s |
   | sftp -R 256 -B 262144, gcm | 101.8 s | 2.52 MB/s |
   | scp gcm, 4 parallel parts | 48.2 s | 5.31 MB/s |
   | scp gcm, 8 parallel parts | 38.8 s | 6.59 MB/s |

   The joined 8 parts hash correctly. Single-stream tuning gains almost nothing, and parallel streams scale, so the limit is per connection in the tunnel. The path goes through the OVH VPS: 10.99.0.1 (about 22 ms), then 10.99.0.2 (about 46 ms). The tunnel MTU can't be probed, because 10.99.0.2 answers don't-fragment pings of every size with "port unreachable". So: `build-gsi.sh` publishes `system.img.partNN` beside the image, and `Get-RemoteImage.ps1` gets `-Streams` (default 8; try 12 and 16, because 8 hadn't levelled off), joins the parts, keeps the SHA-256 check over the joined file, and falls back to the single file when there are no parts. Expected: 1.8 GB in about 4.5 minutes instead of 13.
2. **Make `Deploy-Image.ps1` wait for the charge-limit file** (up to about 60 s) before its report. On build 4 it reported "not applied yet" because the service waits 30 s first. The file appeared 30 s later with `upper_limit=80, blocking=1`.
3. **Pin down what limit 100 does.** Setting `persist.vedotom.charge_limit` to 100 re-applied (`upper_limit=100` in the file), but `blocking` stayed 1 and the battery "Not charging" for 3 minutes at a steady 100%. Confirm the resume condition in `qpnp_adaptive_charge.c`'s `update()`. If it resumes only when capacity drops below the limit, document "100 lifts the limit once the level next falls". Propose any other way to clear the suspend before trying it: no new kinds of write without the user. Never read `upper_limit` or `lower_limit` back. `blocking` is the safe check.
4. **Watch the SystemUI crash.** Once, 7 s into build 4's first boot: SIGSEGV with pc `0x0011c70000000000`, from `nterp_helper` in `androidx.compose.runtime.SnapshotStateKt` (snapshotFlow lambda), then `SnapshotKt.advanceGlobalSnapshot`, then `Recomposer.composeInitial`, then a LazyLayout subcompose. It restarted and stayed up. It wasn't seen on earlier images, and isn't reproduced. In the next image, check the dalvik-cache and odrefresh status for system_ext apps: CompOS left in this build, so look at whether SystemUI now runs interpreted at first boot, and at the tagged-address setting in the crash (`tagged_addr_ctrl: PR_TAGGED_ADDR_ENABLE`).

## 5. From the repository review (2026-11-19)

The install PC's side is fixed and pushed: `dev\VedoTom.psm1` now holds root for either su (`Invoke-RootShell`), the one-device check, `Wait-DeviceBoot -AfterReboot` (`adb wait-for-disconnect` first, so the old system's `boot_completed` isn't read as the new one's) and `Test-GsiRunning` (the first line of `gsi_tool status`, because `ro.gsid.image_running` is empty here). Install-Gsi, Deploy-Image, Set-DevSettings, Dump-DeviceInfo, Trace-Device and `Start-Frida` use it, and all of them were tested on build 4. These are for the build machine, and they fit into build 5:

1. **Stale sidecar files.** When `build.prop` or `vbmeta.img` isn't fetched, the previous build's copy stays next to the new `system.img`, and `Install-Gsi.ps1 -Image` packs it into the DSU zip. This happens in three places: `Get-RemoteImage.ps1` (the `try/catch` around the two pulls; fold this into the parts work in section 4, item 1), `build-gsi.sh` (`cp … build.prop … || true` and the `vbmeta` copy into `DEST_DIR`), and its `PUBLISH_DIR` loop (`continue` on a missing file). Remove each target before copying, and treat a missing `build.prop` as an error.
2. **`apply-local.sh` always exits 0.** It runs with no `set -e`, and `rsync … && echo` and `git apply … && echo` swallow failures, so `build-gsi.sh`'s `|| exit 1` never fires. Add `|| exit 1` to both.
3. **A tag bump is ignored on an existing tree.** `sync.sh` runs `repo init` only when `.repo` is missing. Run `repo init -u "$MANIFEST" -b "$TAG"` every time (it's idempotent), and take `MANIFEST` from `toolchain.json` like the tag.
4. **`build-after-sync.sh` reads old results.** `work/aosp-sync.log` is appended across runs. Any old `sync exit:` line skips the wait, and `grep -q '^sync exit: 0'` accepts an old success after a new failure. Truncate the log, or record its size, at start, and judge by the last line only (`tail -1`).
5. **A charge-limit change can be dropped.** The service sleeps 30 s after writing, and init's `start` does nothing for a oneshot that's still running, so a second `setprop` within 30 s is lost (the property says 85, the module keeps 80). After the sleep, re-read `persist.vedotom.charge_limit` and write again if it changed. Keep to the same two named files: write `upper_limit`, check through `blocking`, and never read limits back. Also remove `$STATE/charge-limit` when the service starts. It survives reboots in `/data`, so Deploy-Image's report (section 4, item 2) could read the previous boot's result.

**Status (build machine, 2026-11-19):** items 1 to 5 are done in the repository, together with section 4's items 1 (parts: `build-gsi.sh` publishes 16 parts and `system.img.parts`; `Get-RemoteImage.ps1 -Streams`, default 8, retries a bad part once and falls back to the single file) and 2 (`Deploy-Image.ps1` waits up to 60 s for the charge-limit file). `build-after-sync.sh` records the sync log's size at start and judges only the last `sync exit:` line written after it, rather than truncating a log a running sync may still be writing. Section 4's item 3 still needs `qpnp_adaptive_charge.c`, which isn't in the AOSP tree.

Smaller, when convenient: patch file names map every dash to a slash, which breaks for projects with dashes in their path (`prebuilts/build-tools`). `JOBS` and the tree directory (`treeDir` in `toolchain.json` is unused) could come from one place.

## 6. Policy decisions (the user, 2026-11-19)

These answer section 4's item 6 and the matching points in section 3. Items 1 and 2 go into **build 6**; build it, publish it, and the install PC deploys and validates it.

1. **ADB authorisation on: `ro.adb.secure=1`.** Set it as a product property (`PRODUCT_PRODUCT_PROPERTIES`, since the GSI's artifact rules forbid system properties). Check on the built `build.prop` files, and then on the device with `getprop ro.adb.secure`, that the product value wins over whatever the system partition sets for userdebug. What changes for deploying: each DSU install has fresh userdata, so it has no `/data/misc/adb/adb_keys`, and the first adb connection after every deploy shows the "Allow USB debugging?" prompt on the phone. `adb wait-for-device` (in `Wait-DeviceBoot`) waits through an unauthorised device, so `Deploy-Image.ps1` blocks until the user taps. Make it print a clear "tap Allow on the phone" line when `adb devices` shows `unauthorized`, so the wait isn't silent. Don't bake any PC's key into the image: the repository is public, and the key belongs to a machine, not to the project.
2. **No Google endpoints for connectivity checks or time.**
   - Captive portal: GrapheneOS's public endpoints, which it runs for any client: `https://connectivitycheck.grapheneos.network/generate_204` (HTTPS), `http://connectivitycheck.grapheneos.network/generate_204` (HTTP) and `http://grapheneos.online/gen_204` (fallback). They return the same 204 as Google's. Prefer a resource overlay on the NetworkStack module (`config_captive_portal_http_url`, `config_captive_portal_https_url`, `config_captive_portal_fallback_urls`; confirm the names against the tag's `packages/modules/NetworkStack/res/values/config.xml` and which package the overlay must target). Fall back to setting `captive_portal_http_url`, `captive_portal_https_url` and `captive_portal_fallback_url` in the first-boot service, as with the development settings, if an overlay on the mainline module isn't practical.
   - Time: `pool.ntp.org`. Android 16's framework resource is the `config_ntpServers` string array (`ntp://time.android.com` upstream), not the old single `config_ntpServer`; confirm it in the tag's `frameworks/base/core/res/res/values/config.xml` and set it in `VedoTomFrameworkOverlay`.
   - Validate it on the device: Wi-Fi shows as connected with no "No internet" mark, `dumpsys connectivity` reports the network as `VALIDATED`, the probes in `dumpsys network_stack` go to the new hosts, and `cmd network_time_update_service` (or `dumpsys network_time_update_service`) shows a time from `pool.ntp.org`. Watch for logcat lines that still name `gstatic`, `google.com` or `time.android.com`.
**Status (2026-11-19):** items 1 and 2 are done and validated on build 7 (8dd9e39): `ro.adb.secure=1`, captive-portal probes to GrapheneOS, NTP from `pool.ntp.org`. Build 6 had set only the singular probe URLs; NetworkMonitor reads the `config_captive_portal_http[s]_urls` arrays first, so build 7 sets those too.

3. **WebView: accept that it ages with the tag** for now. Revisit if an app needs a newer one. Moving the tag (item 4) refreshes it.
4. **Moving the AOSP tag: plan it** as a separate project, for the next Android 16 QPR tag. The image's security patch level is 2025-11-05. That means a sync of the new tag, rebasing the three patches and the `Android.bp` mirror, and a full re-validation. Not part of build 6.
5. **Removing the remaining unused system apps: no.** Mirroring the ~600 lines of upstream system-image definitions to drop BasicDreams, `com.android.egg`, Bips, PrintSpooler, HtmlViewer, BookmarkProvider, CallLogBackup and WallpaperBackup costs more upkeep on every tag move than the space is worth.

## Vendor noise (only fixable outside the image)

- `MotWlc_AIDL` logged 499 errors in four minutes, polling a missing `wireless/device/wlc_st_changed` node. `mtkpower@impl: [setMode] unknown type` logged 87, because the GSI's PowerHAL modes don't match MediaTek's.
